# 温泉番付の公開・並べ替え設計

検討日：2026-10-03 / 対象：採点基準1.2 / 公開先：GitHub Pagesの`docs/`

## 推奨するコンセプト

**温泉地の索引を置き、利用者が選んだ条件と好みから、その場で番付を作る。** 温泉地ごとの固定総合点を主データにせず、根拠のある特徴と、その特徴が成立する浴槽・利用条件を公開する。

初期画面は好み未設定の名前順一覧。利用者が「香りを楽しむ」などの設定例を選ぶか、好みの特徴を追加して重みを指定すると番付になる。設定例は運営が作った一例として重みを明示し、編集できるようにする。強い硫黄臭を好む人と避けたい人は、同じ事実から違う順番を得る。

項目数は固定しない。採点カタログの基本テンプレート、パラメータ付きの評価軸、画面上の選択肢は別の層とする。画面には「追加・検索」で必要な特徴を出し、採点軸を整理・増設しても全画面を作り替えなくて済む構成にする。

## 何を「番付の一行」にするか

| 表示単位 | 採点する実体 | 使い方 |
| --- | --- | --- |
| 温泉地 | 条件適合の浴槽または実行可能な訪問プランのうち、点の下限が最大の一候補 | 通常の番付。採用浴槽・プラン名を必ず添える |
| 施設・浴槽 | 同一浴槽、同一利用区分・時期・運用条件の値 | 特定施設を選ぶ場合。温泉地の詳細から比較 |
| 訪問プラン | 実際に組み合わせられる浴槽・宿・移動・日程の集合 | 複数の湯、宿泊、食事、移動費などを含む依頼 |

一行が温泉地でも、先に浴槽・プラン内で集計し、その後に温泉地へ集約する。浴槽Aの香り100点と浴槽Bの静けさ100点を同じ浴槽の点として足す処理はしない。複数浴槽を巡る条件は、移動・時間・利用可否を含む実行可能なプランとして別途定義する。

「湯の個性の種類数」「町全体の飲食店の選択肢」など地域範囲の指標は、浴槽値とは別の台帳・範囲で作る。同一地域・利用条件に適用可能な値だけをプランへ結び付け、浴槽を増やしただけで他の項目を加点しない。

## スコアとソートの順番

1. 公開データ版、調査範囲、日帰り・宿泊などの比較条件を確定する。
2. 必須条件を生値で判定し、「適合確認」「未確認」「不適合」へ分類する。
3. 適合確認の各浴槽・プランで、利用者が指定した好みの重みを使って点の区間を計算する。
4. 温泉地ごとに点の下限が最大の浴槽・プランを採用する。
5. 温泉地をその下限の降順で並べる。同点は同順位にする。

### 必須条件と好み

「露天があれば嬉しい」は好み。「露天でないと対象にしない」は必須条件。予算、日程、対象年齢、予約の可否なども、依頼の意味に応じて分ける。好みの重みで必須条件違反を相殺しない。

たとえば入浴料の区間が800〜1,200円、上限が1,000円なら未確認。上限900円まで拘束できれば適合確認、下限1,100円なら不適合。料金不明を0円に置き換えない。利用者が指定したAND/ORは三値で評価し、未確認を適合扱いしない。画面では全採点項目を必須条件に使え、AND/OR/NOTを入れ子で組み合わせられる。

### 採点基準1.2との対応

重み`w_i`は−1〜1。未選択・関心なしは0。正の重みは特徴が強い方向を好み、負の重みは弱い方向を好む。元の特徴点の区間を`[L_i,U_i]`とする。

| 状態・好み | 点への寄与区間`[l_i,u_i]` |
| --- | --- |
| 確認した値、正の重み | `[L_i,U_i]` |
| 確認した値、負の重み | `[100−U_i,100−L_i]` |
| U/E/F：未確認・未調査・取得不能 | `[0,100]`。負の重みでも下限への加点なし |
| A：対象外 | `[0,0]`。選択された重みは分母に残す |
| 重み0 | 採点に使わない |

`D = Σ|w_i|` として、プランの点は `S_L = Σ|w_i|l_i / D`、`S_U = Σ|w_i|u_i / D`。`D=0`なら総合点も順位も作らない。Xの矛盾は根拠から拘束できる区間を使う。根拠取得率は同じ実効重みでK/C/Zを集計し、点へ掛ける係数にはしない。

各項目の重みは数値入力で−1〜1の任意値を指定できる。分野予算を指定する場合は、分野内の絶対重みを正規化してから分野間で配分する。正の予算に有効項目がない設定は計算を止め、全予算0は未算出とする。点・区間・根拠取得率・数値確定度は同じ実効係数を使う。

数値・件数の特徴には希望帯の下限a、上限b、減衰幅dを指定できる。同じ生値からT(a,b,d)で適合点を再計算し、その項目の元の尺度を置き換える。帯の中は100点、帯からdだけ離れると0点。生値が区間の場合は、端点と区間内の頂部を含めて点の包絡を求める。a≤b、d>0を満たさない設定・未入力では順位を作らない。

### 代表候補と不確実性

採用候補の`[S_L,S_U]`と、候補集合で最良を選ぶ場合の`[max S_L,max S_U]`を区別する。後者の上限が別浴槽から来ることはあるが、採用浴槽の点として表示しない。順位は`max S_L`だけで決める。未確認の代替浴槽があることも示す。

区間は根拠によって拘束できる範囲で、確率・信頼区間ではない。区間が重なる候補の優劣は確定しない。上限順や中点順を標準順位にすると資料の乏しい候補が上がりやすいため、採用しない。

### 表示順と順位

| 操作 | 表示の動作 |
| --- | --- |
| 初期状態／好みリセット | 名前順、点・順位なし。必須条件は保持 |
| 適合点順 | 点の下限の降順。未丸め値で同点を判定し、1位・1位・3位方式 |
| 名前順 | 表示だけを変える。好み設定済みなら算出した順位を保持 |
| 根拠取得率順 | 情報の揃い方を見る表示順。点の順位を保持 |
| 未確認／条件外タブ | 順位なし。理由と対象の浴槽を表示 |

同点の表示順、同じ点の代表候補は名称・IDで安定させる。料金・所要時間・距離の単独ソートを増やす場合は、対象・単位・利用条件を合わせた生値を使い、未知は末尾または別一覧にする。日帰り入浴料と宿泊総額を同じ料金列で混ぜない。

## 多施設の温泉地の日帰り料金

「ある施設を安く利用できる」と「温泉地全体が手頃」は別の質問である。日帰り料金は次の軸に分け、利用者が指定した軸だけ採点する。

| 質問 | 項目・表示 | 集約 |
| --- | --- | --- |
| 採用する施設でいくら払うか | Y01・採用候補の入浴料 | 同じ候補の税込必須総額。必須予算の判定に使う |
| 地域の通常料金はどの程度か | Y23・料金中央値の安さ | 各施設の通常最安料金を一件ずつ、中央値で集約 |
| 指定予算内で何施設を選べるか | Y24[budget=1000]など | 予算内の施設数。固定尺度N(10) |
| 地域の何割が予算内か | Y25[budget=1000]など | 予算内施設数÷全対象施設数 |
| 安く入れる通常施設があるか | 地域最低料金の表示 | 全対象施設の通常最安料金の最小値。中央値とは別に表示 |

一般成人1名・非住民非会員・公表通常料金・入浴のみを共通条件とし、税と必須費用を含める。タオルを持参できる施設では持参する。平日と土日祝は別の母集団にする。料金水準の系列は入場時刻の指定なしで、公表入場時間内の通常券を比較する。到着時刻や滞在時間を指定した依頼は別の条件に分ける。貸切、食事必須、宿泊、休憩付きパッケージ、割引券は別系列。同じ券で複数浴槽を使える場合も施設は一件である。各施設の通常券の選択肢を調べ切る前に、取得した一券を施設の最安値と確定しない。

10施設のうち1施設だけ500円、残り9施設が1,800円なら、料金中央値は1,800円、1,000円以下は1施設・10%。10施設すべて500円なら、中央値500円、1,000円以下は10施設・100%。最安500円という一値だけではこの差を表せない。施設が11以上になっても定義と尺度を変えず、他の温泉地の最大値で正規化しない。

料金未知の施設も分母に残す。全施設が確定している場合、予算内確認数をs、予算超過確認数をf、施設数をNとして、予算内件数は[s,N−f]、割合は[s/N,(N−f)/N]。施設母集団・所属が未確定なら、地域最低料金・中央値・割合は未算出Eとする。予算内件数の下限sは残せるが、上限は未確定。全対象が0施設と確認された場合は対象外Aであり、無料の地域とはしない。

今回の10温泉地では施設母集団も通常券の選択肢も未完成である。取得集合の参考最低料金・参考中央値を地域値と分け、通常入浴の提供が確認された施設でも通常券の料金行が未取得なら残す。たとえば休憩付きの料金しか収録していない施設で、通常入浴のみの提供が確認されている場合、施設自体は対象に残し、休憩付き券を通常料金集計から外す。

[日帰り料金の比較画面](./fees.html)はこの区別と施設ごとの調査残を表示する。地域の予算内割合が高いことだけで、番付で採用した施設のY01の予算条件を通過させない。詳しい定義は[採点基準第6.7節](./criteria/scoring-1.2.md)に記載した。

`research/regions/`の独立した調査入力を`build_public_data.py`で変換し、10地域の`ledgers/`と閲覧用レポートを生成する。`docs/`外の原本は編集・調査用、`docs/`内は検証して公開する成果物。生成段階で旧ID・別名を正規評価軸へ解決し、同一軸の重複登録を拒否する。集約ビューと内訳の重複は明示的な指定がある時だけ許す。カタログ249テンプレートとパラメータ付きビューを固定列のCSVにしない。

| 公開ファイル | 保持する情報 |
| --- | --- |
| manifest | 形式版、採点基準版、データ版、公開日、各ファイルURL、対象件数 |
| regions | 安定ID、温泉地名、読み、地域。固定総合点は持たせない |
| ranking | 候補ID、温泉地ID、利用条件、正規評価軸、状態、特徴点区間、生値区間・単位。目標値適合に必要な生値も残す |
| ledgers | 浴槽・施設・源泉ID、出典URL、確認日、対象期間、条件、値の採用理由、矛盾・未確認理由 |
| views | 正規キー、説明、方向、単位、入力方法、比較範囲、対象となる条件。動的項目はカタログに基づき生成 |

台帳→条件整合・区間変換→公開JSONの生成を公開前に行い、ブラウザでは重みと必須条件を変えて計算する。GitHub PagesはHTML/CSS/JavaScriptを配信する静的ホスティングなので、この分担ならサーバーの採点APIは不要。[GitHub公式：GitHub Pagesについて](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)

生値が比率か%か、静けさが騒音の反転か、料金が何人・何泊分かを生成時に固定する。公開する比率値は採点基準どおり0〜1で保存する。K/Zの数値には両端、Cには根拠のある片側または両側の境界が必要で、U/E/Fの生値はnullとする。源泉の分析試料を、供給対応の未確認な浴槽の現在値に転用しない。

平日と土日祝は候補を先に分け、温泉地ごとの最大点を取る。比較日を定義したことと、その日の営業・運行・空室・価格を確認したことを区別する。現在の60プランは公表条件の初回整理であり、指定日の予約成立を保証するデータではない。

## 全件性・更新・再現性

- 対象範囲の索引と候補ベクトルを読み終えてから、その範囲の順位を確定する。画面には比較件数・調査範囲・データ版を出す。
- 規模が増えたら地域・利用モード等で候補を分割する。各分割の一覧・件数をmanifestで管理し、全国番付には全国の必要な分割を読む。画像・詳細台帳だけはクリック時に取得できる。
- 通信失敗・読込中は採点状態U/E/Fと別扱い。読めなかった候補を未知の値で補って完成した順位にしない。
- データ版・基準版・形式版の混在を検出したら計算を止める。公開済みreleaseを上書きせず、新しいreleaseを追加し、検証後にmanifestを切り替える。
- 共有URLには基準版・データ版・正規評価軸・重み・必須条件・比較範囲・表示順を含める。点や順位は保存値を信用せず再計算する。本番は旧releaseも選択して復元できるようにし、廃止した版は利用できない理由を表示する。
- 今回の試作は単一releaseだけを読む。異なる版の共有設定を現行版へ黙って置き換えず、読込エラーにする。

変動する料金・営業・交通の条件には確認日と有効期間を残す。現在利用できるかと、過去に確認した湯の特徴は区別する。調査範囲を広げる場合も、全項目が未確認な温泉地を不存在として消さない。

## 画面構成

上から①比較範囲・利用条件、②必須条件、③好み設定、④番付、⑤内訳・出典の順。PCは左に設定、右に結果。スマートフォンは設定を開閉し、結果カードを縦に並べる。

一行には温泉地名、順位、採用浴槽・プラン、点の下限と幅、根拠取得率を載せる。内訳では生値、状態、好みの方向、重みを反映した寄与、適用条件を見られるようにする。未確認・条件外にも戻り口を用意し、件数が0でも必須条件を自動で緩めない。

選択UIは「追加」検索＋分野の分類＋パラメータ入力を使う。全249基本テンプレートと公開済みの条件別項目を読み込み、未調査の特徴も選べる。追加時の重みは0で、利用者が入力した値のみ採点に用いる。未調査の有効項目はE・[0,100]として重みの分母に残し、番付を暫定表示する。「pHが低い」「pH4〜6に近い」は別の選び方として入力し、目標値ビューを生値から生成する。年齢・人数・時期・言語・移動手段などは評価軸のパラメータ／比較条件として表し、単なるタグで済ませない。

## 試作で確認できることと、本番で必要なこと

番付設定はデータ件数や代表項目数で制限しない。採点カタログの全項目、パラメータ付き項目、任意の数値重み、希望帯、分野予算、再帰AND/OR/NOT条件、三値分類、利用区分、温泉地への集約、内訳、共有URLを扱う。共有設定には計算に必要な値を保存し、元のデータ版で再計算する。旧形式の露天・料金条件も新しい条件式へ復元する。

架空の公開デモ6地域・9プランは削除し、指定10温泉地の根拠付き初回部分調査へ置き換えた。選択できることと調査済みであることを区別し、データ版の調査範囲を画面に表示する。利用区分・曜日に候補が未収録の地域も未調査として残す。

各試行はその地域の調査入力・料金分類と採点基準のみを使い、他地域の点・標本最大最小・順位を参照しない。単独生成とまとめて生成した結果の一致を検証する。固定比較台帳が必要な希少性の項目は、今回の資料だけで数値を作らない。

現行公式一覧の温泉キャラクター135人を照合し、有馬の2人を同じ地域へ対応させた134の地域調査候補を保存した。親地域と下位地区の重なりを含むため、134の独立した地域が確定したという意味ではない。指定10地域以外の124候補は未調査。130に件数を合わせて追加地域を切り捨てず、施設集合・境界・入浴可否を地域ごとに確認する。

本番化は次の順番がよい。

1. 実在データを少数地域で整備する。安定ID、浴槽・条件、生値・出典・確認日をそろえ、全件性と更新単位を決める。
2. 台帳から公開データを作る検証付き生成処理を用意する。正規化・別名解決・重複軸・条件整合・版混在を検出する。
3. 調査範囲と条件付きの生値を広げる。年齢・言語・日時など利用条件が一致した根拠を結び付ける。
4. 宿泊・複数浴槽・移動等の訪問プランを扱う。実行可能性を確認するための所要時間・営業・移動の根拠を追加する。

採点モジュールは正規化済み区間を受け取り、生成処理は今回取得した根拠の固定尺度への変換を扱う。追加の比較台帳を必要とする尺度、旅程探索・自然文リクエスト解析は未実装。10地域とも全249項目・全構成施設・全条件の調査は未完了である。検証書にある実在10温泉地の旧集計は、現行の実在浴槽・条件付き台帳へ自動流用していない。
